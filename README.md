> branch contains **no robot code** — only the setup scripts that create a new project from
> one of these branches.

Use this as your starting point when reading the documentation or setting up a new
robot. Every file is written to be **readable first** — no competition pressure, no
half-finished experiments, no commented-out blocks. It mirrors the structure and
best practices of the latest competition robots (drumbot, cube-bot).

> **The library is imported as `import raccoon`.** It was formerly called `libstp`;
> if you find `from libstp import ...` in old code, that is outdated — use `raccoon`.

## What This Robot Does

ExampleBot is a simple delivery robot:

1. **Setup** — homes the servos, asks for a table-side parameter, calibrates the line
   sensors and drive distance, then waits for the light start.
2. **Navigate** — drives to an object using heading control and a line-sensor stop.
3. **Collect** — picks up the object with an arm and claw, then wall-aligns to reset
   heading error.
4. **Deliver** — follows a line to the drop-off zone, deposits the object (and records
   it via a stateful service), clears the area.
5. **Shutdown** — leaves the robot safe when the match timer elapses.

The task is intentionally simple so the *code structure* is the focus, not the game
logic.

> `src/hardware/defs.py`, `defs.pyi` and `robot.py` are **generated** from the `config/`
> YAML by `raccoon run` (or `raccoon codegen`) and are git-ignored, so they are not in
> a fresh checkout. Run `raccoon codegen` once if you want to read them next to the
> YAML. To make a permanent hardware change, **edit the YAML**, never the generated
> Python.

## The Three Layers

RaccoonOS projects separate concerns strictly (see [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md)):

| Layer | Directory | Responsibility |
|:------|:----------|:---------------|
| **Mission** | `src/missions/` | *What* to do, in order. Declarative sequencing only. |
| **Step** | `src/steps/` | *One* reusable action. A `@dsl` factory + optional `Step` subclass. |
| **Service** | `src/service/` | Shared, stateful logic via `RobotService`, reached with `robot.get_service(...)`. |

Flow for a new feature: **mission → step → service**.

| File | Concepts |
|:-----|:---------|
| `raccoon.project.yml` | `format_version: 2`, config includes, run configurations |
| `config/hardware.yml` | Sensor / motor / servo declarations, `SensorGroup`, `!include-merge` |
| `config/robot.yml` | Kinematics, PID gains, axis constraints, physical geometry |
| `config/run-configurations.yml` | Named run profiles + env flags (`RACCOON_CMD_TRACE`, …) |
| *(generated)* `hardware/defs.py` | `Motor`, `IRSensor`, `SensorGroup`, `ServoPreset` with named positions — built from `hardware.yml` / `motors.yml` / `servos.yml` |

| `mission_params.py` | `ParamSet` / `NumberParam` — table-side tuning (`.ask()` / `.get()`) |
| `m000_setup_mission.py` | setup timer, `run_unless_no_calibrate`, `collect_drive` + `calibration_gate` |
| `m010_navigate…` | `mark_heading_reference()`, `parallel()`, `drive_forward(until=…)`, compound conditions |
| `m020_collect…` | reusable composite step, `wall_align_backward()`, re-marking heading |
| `m030_deliver…` | `follow_line_single()`, `&`/`+`/`|` stop-condition operators, service call |
| `m999_shutdown…` | leaving the robot safe (`fully_disable_servos()`) |
| `steps/arm_steps.py` | `seq()` composition, eased servo moves, `defer()` for runtime decisions |
| `steps/delivery_steps.py` | custom `Step` subclass, `robot.get_service(...)` |
| `service/delivery_tracker_service.py` | `RobotService`, `ClassNameLogger` logging |

## Quick Start

The easiest way to start a new robot from this example is the setup script. It installs
git and uv if needed, asks for a project name and drivetrain type, clones the matching
branch, renames the project, creates a fresh git repository with its own `uuid`, runs
`uv sync` and makes the first commit. Run it in the folder you want the project in:

**Linux / macOS**

```bash
curl -LsSf https://raw.githubusercontent.com/htl-stp-ecer/raccoon-example/main/raccoon-setup.sh | bash
```

**Windows (PowerShell)**

```powershell
irm https://raw.githubusercontent.com/htl-stp-ecer/raccoon-example/main/raccoon-setup.ps1 | iex
```

Then activate the virtual environment, connect to your Wombat and run:

```bash
cd <your-project>
source .venv/bin/activate        # Windows PowerShell: .venv\Scripts\Activate.ps1
raccoon connect <PI_ADDRESS>
raccoon run
```

The first `raccoon run` generates `src/hardware/` from the YAML, so there is nothing
to build by hand.

<details>
<summary>Setting it up manually instead</summary>

```bash
git clone -b differential --single-branch https://github.com/htl-stp-ecer/raccoon-example.git
cd raccoon-example
uv sync
```

**Give your copy its own identity first.** In `raccoon.project.yml`, set `name:` (and the
`name` in `pyproject.toml`) and replace the placeholder `uuid: change-this` with a fresh
UUID (`python3 -c "import uuid; print(uuid.uuid4())"`). The UUID decides which folder on
the Wombat (`/home/pi/programs/<uuid>`) holds your project — two projects with the same
UUID overwrite each other when deployed to the same robot.

</details>

See [Getting Started](https://raccoon-docs.pages.dev/00-quick-start) if this is your
first time. For fast iteration use a run profile: `raccoon run --config dev`.

## Logging

RaccoonOS captures nearly everything a run did to a structured JSONL log, with exact
source locations and timings. This is the fastest way to debug.

```python
from raccoon import info, debug, warn, error   # log from anywhere
info("Reached pickup zone")
```

After a run, artifacts land in `.raccoon/runs/<run_id>/` — `libstp.jsonl` (the
full log), `localization.jsonl`, `profile.json`, `cmd_trace.robot.jsonl`,
`sensors.mcap`, and more. **Full guide: [`docs/LOGGING.md`](docs/LOGGING.md).**

## Adapting to Your Robot

### Hardware setup (`config/*.yml`)

Your physical hardware is described entirely in the YAML files: motor ports and
`inverted` flags in `config/motors.yml`, servos in `config/servos.yml`, sensors in
`config/hardware.yml`, and the drivetrain geometry in `config/robot.yml`.

> ## ⚠️ Units: kinematics values are in **meters**
>
> `wheel_radius`, `wheelbase` and `track_width` in `config/robot.yml` must be entered in
> **meters**, not centimeters or inches. Convert first: mm ÷ 1000, cm ÷ 100,
> inches × 0.0254 (e.g. 16 cm → `0.16`). The `physical:` section of the same file is the
> exception — its keys end in `_cm` and are in **centimeters**.

### Performance tuning (`raccoon calibrate`)

`raccoon calibrate` runs an automatic characterisation sweep (encoder resolution,
velocity feed-forward, motion constraints) and writes the values into your config.
The in-run calibration step in `m000_setup_mission.py` additionally auto-corrects small
deviations at the start of every run.

### Motion constraints (`config/robot.yml`)

The `linear` / `angular` blocks under `motion_pid` set top speed and braking profile.
**These must not be zero** — a missing or zero `max_velocity` makes the robot sit still
even when commanded to move. `raccoon calibrate` measures and writes these for you.

### Differential notes

This branch is the **differential** variant (the `mecanum` branch is the four-wheel one).
The drivetrain is defined in `config/robot.yml` (`type: differential`). Its `wheelbase` is
the distance between the left and right wheel contact points (what other drivetrains
call the track width), in meters. The two motors are in `config/motors.yml`.

If the robot drives wrongly the first time, test one wheel at a time (BotUI > Motors):
both wheels should spin **forward** for a positive command. A wheel that spins backwards
needs its `inverted:` flag flipped. A robot that spins instead of driving straight has
one inverted flag wrong.
